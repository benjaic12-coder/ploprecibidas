## Cambios por punto

1. **Caché y deploy.** `_headers` aplica `no-cache, max-age=0, must-revalidate` a páginas y archivos sin hash. `/assets/*` elimina esa regla y aplica `public,max-age=31536000,immutable`. El build agrega `X-Plop-Deploy` con el commit y genera `/deploy.json`. API usa `no-store`. No se cambiaron precios ni combos.
2. **Condiciones.** `/condiciones` tiene título, descripción, canonical y contenido HTML propio, disponible incluso sin JavaScript. Contiene cancelación, cambio de fecha y destino de la seña, producción, saldo, cambios tras aprobar, retiro y envío, todos con `COMPLETAR`. Conserva enlace del footer y sitemap. Se agregaron las cuatro preguntas exactas al FAQ. El build genera un `404.html` real, sin redirección automática. Solo seguimiento y campañas tienen rutas dinámicas explícitas: una dirección desconocida ya no recibe la home.
3. **Admin.** Se eliminó el botón de crear acceso y las instrucciones técnicas de Supabase. Quedó login individual, recuperación y ayuda genérica. Si falla la autorización al recargar, se oculta el panel y se limpian los pedidos visibles. La API valida el usuario con Supabase Auth, email confirmado, sesión no anónima y `plop_staff_email`, antes de consultar datos. RLS usa la lista privada `plop_private.staff` mediante `is_staff()`.
4. **Noindex.** `_headers` cubre `/admin*`, `/pedido/*` y `/baja*`. Admin, recuperación, baja y shell del seguimiento incluyen meta robots desde el HTML inicial. La Function de seguimiento agrega la cabecera también en respuestas dinámicas. `robots.txt` se conservó sin cambios.
5. **Testimonios.** La sección completa desaparece si no hay registros válidos. `public/testimonios.json` usa `nombre`, `carrera`, `texto`, `foto`, `autorizacion`. Solo se muestra `autorizacion: true` con campos completos y foto local. Los bloques `COMPLETAR` nunca se publican. Se conserva el aviso de imagen de referencia del catálogo.
6. **Responsable y conservación.** Footer, privacidad y condiciones usan los campos compartidos de `lib/conditions.ts`, incluido domicilio. `/privacy` tiene plazos de conservación de pedidos y comprobantes marcados `COMPLETAR`. No se inventó una eliminación automática.
7. **Seña y comprobantes.** Se quitaron los datos bancarios de la confirmación en la home; están en el seguimiento. `lib/payment-config.ts` centraliza el adaptador de configuración y los límites del formulario. Los valores vigentes siguen teniendo una única fuente persistente: `plop_settings`, fila `public`, editable desde Admin → Configuración; no se duplican ni reemplazan datos bancarios existentes. El seguimiento muestra la seña calculada por servidor y lo pendiente luego de pagos verificados. Comprobantes: JPG/PNG/WebP/PDF, máximo 5 MiB, rechazo de vacíos y validación de firma/MIME en servidor. Bucket privado existente `plop-v2-comprobantes`, límite 5.242.880 bytes. Lectura del archivo por el equipo con URL temporal; el archivo no confirma un pago automáticamente. Se conservaron y verificaron los estados pendiente / comprobante recibido / seña verificada / saldo pagado y la acción “Marcar verificado”.
8. **Hero.** `Plop` es texto real accesible, junto al logo decorativo; mantiene el aspecto. El HTML inicial también contiene “Te recibís. Lo celebrás. Lo hacés con Plop.”.

Las tablas de colas y otras tablas internas con RLS sin políticas quedan cerradas a anon/authenticated. El alta y seguimiento de pedidos usan la API protegida; no se agregaron permisos públicos de lectura de pedidos ni de escritura en Storage. Las tablas privadas staff/rate_limits están fuera del esquema público y no dependen de RLS para su aislamiento.

Se ejecutó una prueba real de RLS en una transacción revertida con rol authenticated no autorizado: `is_staff=false`, pedidos visibles=0, pagos visibles=0, comprobantes visibles=0. Se consultó Security Advisor: sus avisos de rol authenticated en políticas de equipo se contrastaron con la función, que excluye anónimos; los avisos no prueban por sí solos una filtración. La protección de contraseñas filtradas de Auth figura desactivada.

### Acciones manuales de Supabase

No se cambiaron tablas, buckets, políticas, Auth ni Edge Functions en producción en esta entrega. Se conservaron los existentes tras verificarlos. Quedan estas configuraciones concretas:

1. **Registro de cuentas.** Preparado `docs/cerrar-registros-publicos.sql`: ejecutar en SQL Editor y luego seleccionar `public.plop_before_user_created` en Authentication → Hooks → Before User Created (Postgres). Rechaza correos ajenos a la allowlist y admite las sesiones anónimas del checkout. No apagar globalmente “Allow new users to sign up” con esta arquitectura: Supabase también bloquea los nuevos usuarios anónimos y dejaría de funcionar el checkout en navegadores nuevos. Si se quiere apagar ese interruptor global, primero hay que reemplazar el alta anónima del checkout. Conservar email/password para que ingrese el equipo existente y confirmación de email activa. Crear/invitar nuevas cuentas del equipo desde el dashboard, incluyendo antes su correo en la allowlist privada.
2. **Endurecer reseñas públicas.** Ejecutar `docs/restringir-resenas-publicas.sql`. Elimina solo `reviews_public`; las reseñas aprobadas siguen disponibles mediante `/api/reviews`, que proyecta únicamente los campos públicos, y la nueva sección usa JSON. El equipo mantiene su política propia. No toca pedidos ni pagos.
3. Confirmar alias, CBU/CVU, titular y banco en Admin → Configuración. No es necesario crear otro bucket ni ampliar permisos. La seña se calcula con importes del servidor.
4. Cuando definas conservación, implementar y probar la eliminación/anonimización de registros y archivos correspondiente. El placeholder no crea una tarea de borrado.

Referencias verificadas: https://supabase.com/docs/guides/auth/auth-hooks y https://github.com/supabase/auth/blob/master/internal/api/anonymous.go (el interruptor global también se comprueba para el alta anónima).

## Cloudflare: purga y verificación

1. Entrar a Workers & Pages → plop-recibidas → Deployments y comprobar que el deploy de producción terminó en Success con el commit nuevo. Abrir su URL inmutable `<id>.plop-recibidas.pages.dev`.
2. En el dominio actual `pages.dev` no hay una zona propia para usar “Purge Everything”. Cada publicación de Pages actualiza su caché; si hiciera falta, volver a publicar el commit correcto y comprobar el alias de producción. “Purge build cache” limpia la compilación, no la caché que ve el visitante.
3. Si se incorpora un dominio propio administrado en Cloudflare: seleccionar esa zona → Caching → Configuration → Purge Cache → Custom Purge por URL, o Purge Everything para toda la zona. No agregar reglas “Cache Everything” para HTML/API.
4. Abrir sin caché del navegador `/`, `/condiciones`, `/privacy`, `/admin` y un seguimiento válido. Comparar `X-Plop-Deploy` con `/deploy.json` y con el commit del deploy. Los cuerpos de home y condiciones deben diferir; sus ETag también pueden diferir legítimamente. El identificador de versión debe coincidir.

```bash
curl -sSI https://plop-recibidas.pages.dev/
curl -sSI https://plop-recibidas.pages.dev/condiciones
curl -sS https://plop-recibidas.pages.dev/deploy.json
curl -sSI https://plop-recibidas.pages.dev/ruta-inexistente-plop
```

Guías: https://developers.cloudflare.com/pages/configuration/serving-pages/ y https://developers.cloudflare.com/pages/configuration/headers/.
